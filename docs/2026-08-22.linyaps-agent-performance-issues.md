# debian-rules-to-linyaps Agent + Skills 性能问题分析报告

> 日期：2026-08-22
> 依据：`examples/2026-08-22.token-usage-analyze.md` 高 token 消耗报告 + 对当前仓库 `agents/`、`for-multica/`、`skills/` 的逐文件交叉核验。
> 范围：分析 agent + skills 存在的性能问题与代码定位；不改动既有文件。

---

## 一、报告要点回顾

`2026-08-22.token-usage-analyze.md` 在 444 个 session 中识别出 **97 个 >400 万 token 的高消耗 session**（占 22%，token 约占全量 49%）。核心结论：

> **高 token 不在"内容多"，而在"回环多"**。思考高度集中在三类行为：
> 1. **构建/监控回环**（bash 高频 + 上下文持续膨胀）
> 2. **技能/路径/接口探索**（`skills/` vs `.opencode/skills/` 路径不一致 → 反复定位）
> 3. **校验往返**（YAML 版本格式 → edit→validate→read 长回环，obs-studio 17.3M 为典型案例）
>
> 根因不是内容复杂度，而是**模型反复在理解现状、找脚本/路径、配技能调用、验证 YAML、盯构建**上迭代，把已增长的上文不断重新编码进 input。

## 三、确认的性能问题（含代码定位）

### 问题 1：多策略"搜索"散文驱动技能/路径探索回环（对应报告行为 B）

**报告对应**：`技能加载与脚本接口探索` 主题 606 次命中 / 4.65 亿 token；根因 #3「技能实际路径与 AGENTS.md 声明的 `skills/` 不一致 → 模型反复 ls/read/find 定位」。

**代码定位**：
- `agents/debian-rules-to-linyaps.agent.md:166-186`「Workspace 根目录检测」——教模型「向上遍历父目录最多 5 层 / 客户端目录搜索」；
- `agents/debian-rules-to-linyaps.agent.md:188-211`「Skills 查找策略」——列出多分支定位方式（skill() 加载 / `cat skills/.../SKILL.md` fallback）。

> 多分支 + 遍历性描述，鼓励模型在根目录里反复寻找 skills 的位置，低收益定位往返推高上下文。

### 问题 2：YAML 版本格式无确定性归一 → 校验往返回环（对应报告行为 C）

**报告对应**：obs-studio 最高 17.3M token；根因 #4「YAML 版本格式 `30.2.3+dfsg-3deepin1` → 需 `30.2.3.0`，配合 edit 位置错放，演化为 20+ 轮 edit/validate/read 往返」。

**代码定位**：
- `skills/src2linyaps.debian.build-res-generate/scripts/generate-linglong-yaml.py:379`——`version = get_value(args.package_version, defaults.get('version', '0.0.0.1'))` 直接把 Debian baseline（如 `30.2.3+dfsg-3deepin1`）写入 YAML，**无任何归一化逻辑**（grep norm/sanitize/regex 0 命中）。
- `skills/config/linglong-defaults.json` 的 fallback `0.0.0.1` 是合规 4 段，反而通过——造成「脚本产出版本失败 vs 默认值成功」的割裂，模型被迫手工 edit 试错。

### 问题 3：通用约束在多个文档重复叙述 → 每次加载放大固定上下文

**报告对应**：`为每条思考都把已增长的上文重新编码进 input`；重复的散文约束推高每个 session 的固定加载量。

**代码定位**（同一约束跨文件重复）：
| 约束 | 出现文件数 | 示例定位 |
|------|-----------|---------|
| `${PREFIX}` 安装目录 | 6 | agent.md:128-132、for-multica/agent.md:376、analyze-rules SKILL:101、build-res-generate SKILL:106、analyze-args SKILL:53、src2linyaps.debug SKILL:151 |
| DESTDIR 黑名单 | 6 | agent.md:135-141、for-multica/agent.md:374-380、analyze SKILL 等 |
| 多包合并 | 2 | agent.md:109-111、for-multica/agent.md:369-371 |
| 运行时依赖存在性核验 | 3 | analyze-control SKILL:83、build-res-generate SKILL:105、for-multica/agent.md:373 |
| linglong-defaults / linglong-schema 引用 | 3-4 | 各生成/校验 SKILL |

> multica 平台是**把每个 skill 文件复制到具体 skill 目录**交付的，无法跨目录 import；这是约束重复的机制性根因。

### 问题 4：`agent_config_path` 参数漂移（对应报告"技能调用接口与脚本实际 usage 不符"）

**代码定位**：
- 各 SKILL 输入表将 `agent_config_path` 声明为 string 输入（如 analyze-control SKILL:28、analyze-rules SKILL:28 等），
- 但实测**仅** `skills/linyaps-src-init-dispatch/scripts/dispatch.sh:31` 真正读取，且为**硬编码** `REPO_ROOT/for-multica/agent-config.json`，
- 其余脚本不消费该参数。模型按文档传参却无实际效果，属「接口声明与实现不符」。

### 问题 5：`${tag}` 即时解析的重复强调

**代码定位**：`agents/debian-rules-to-linyaps.agent.md:90-95`、`for-multica/agent.md:54-59`——强制每次会话 `date +"%Y-%m-%d"` + 手动替换，属反复低收益工具调用。

### 问题 6：路径拼写错误

**代码定位**：
- `skills/src2linyaps.debian.build-res-generate/referance/`（应为 `reference/`），generate:143,367 与 validate:107,305 均命中该错名；
- `skills/src2linyaps.debug/ll-builder.command.refence.md`（`refence` 应为 `reference`）。

### 问题 7：`for-multica/agent-config.json` 自相矛盾

**代码定位**：
- `for-multica/agent-config.json:3` `projects_repo` 为空，但 `for-multica/agent.md:52/381` 称「必须非空否则阻塞」；
- `for-multica/agent-config.json:18-21` `trusted_domains` 的 extension `path` 为空，实际值内嵌于 `global.trusted_domains`。

## 四、性能影响量化（定性）

| 问题 | 行为签名 | 相关 token 量级（>400 万 sessions） |
|------|---------|------------------------------------|
| 问题 1（探索） | read/glob/skill 高频，穿插 bash find/ls | ~4.65 亿（"技能加载与脚本接口探索"主题） |
| 问题 2（校验回环） | edit 与 read 高频交替 + validate/schema | obs-studio 单项 17.3M；"YAML/版本格式校验往返" ~4.61 亿 |
| 问题 3（重复上下文） | 每次加载放大固定输入 | 放大所有上述主题 |
| 问题 4（参数漂移） | 传参无效 → 重新找接口 | 低收益往返 |

---

## 五、结论

高 token 消耗主要由**可脚本化/文档化的确定性缺陷**驱动，而非内容复杂度：
1. 减少"搜索散文"即可显著遏制探索回环；
2. 版本归一化下沉到脚本可根除 obs-studio 式校验回环；
3. 约束单一化为专用 SKILL + agent 一次加载，可降低每次加载的固定上下文。

具体改动方案见 `docs/2026-08-22.linyaps-performance-fix-plan.md`。
